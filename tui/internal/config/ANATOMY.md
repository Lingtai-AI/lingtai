# config — bootstrap, venv, global config

> **Maintenance:** see `lingtai-tui-anatomy` (at `tui/internal/preset/skills/lingtai-tui-anatomy/SKILL.md`).

This package manages the TUI's bootstrap sequence — the steps that run before any agent launches. It owns the Python runtime venv, the lingtai CLI upgrade path, addon verification, and the global config files under `~/.lingtai-tui/`.

## Components

- **`tui/internal/config/venv.go:32-117`** — runtime environment marker call site for `~/.lingtai-tui/runtime/venv/.lingtai-env.json`. Marker schema/evaluation/stamping are owned by the installed Python runtime via `python -m lingtai.venv_resolve env-marker {check,stamp} --venv <path>`; Go only consumes the high-level `missing` / `match` / `mismatch` / `error` result. Delegation failures, invalid output, and checker errors are treated as `unknown` and never delete the managed venv.
- **`tui/internal/config/venv.go:169-190`** — `NeedsVenv`: returns true when the managed runtime venv is missing, cannot import `lingtai`, or the delegated marker check returns a confirmed mismatch. A working legacy venv without a marker is accepted and stamped best-effort after the import probe succeeds. Unknown marker checks do not by themselves force deletion/recreation. A working PyPI wheel may still need conversion to local editable/dev mode; that is handled by the separate, consent-gated `CheckUpgrade` / `UpgradePythonRuntime` path instead of recreating the whole venv.
- **`tui/internal/config/venv.go:174-262`** — `EnsureVenv`: creates the runtime venv at `~/.lingtai-tui/runtime/venv/`. Uses `uv` if available (can auto-download Python 3.13), falls back to system Python. If the delegated marker check proves the managed venv belongs to another environment, removes that stale managed venv before invoking `uv venv` / `python -m venv`; unknown/error marker states are left in place. Verifies Python 3.11+, installs `lingtai` from the pinned kernel GitHub release wheel (see the release-manifest row below), asks the kernel-owned marker command to stamp best-effort, and symlinks CLI into PATH. On a dev machine, it installs the discovered `lingtai-kernel` checkout editable rather than PyPI when creating a fresh runtime; this is separate from Windows `install.ps1 -Latest`, which uses a non-editable local build and records `kernel_source: main`.
- **`tui/internal/config/venv.go` (kernel release install)** — `fetchKernelReleaseManifest` / `selectKernelWheel` / `venvPythonTag` / `kernelWheelInstallURL` / `kernelInstallCommand` / `ensureVenvInstallCommand` / `runtimeUpgradeCommand`: the in-venv kernel install now resolves the `lingtai.kernel.release/v1` manifest published on the kernel's latest GitHub release (`releases/latest/download/lingtai-kernel-release-manifest.json`), picks the wheel matching the managed venv's `cp<major><minor>` tag and this host's platform tag, and installs it by pinned URL with a `#sha256=` fragment — never `pip install lingtai` from PyPI or any other index. Both install paths (`EnsureVenv` step 2 and `UpgradePythonRuntime`'s upgrade, which adds `--upgrade`) share this resolution; a manifest fetch, schema, platform, or no-matching-wheel failure is surfaced as an error/`DoctorFail` rather than falling back to an index.
- **`tui/internal/config/devmode.go:64-88`** — `findDevCheckouts`: discovers local LingTai development workspaces only through the explicit `$LINGTAI_DEV_ROOT` contract. The env var points at a root that directly contains sibling `lingtai-kernel/` and `lingtai/` checkouts. A workspace is valid when `lingtai-kernel/pyproject.toml` exists and a sibling `lingtai/` TUI repo exists. Only `lingtai-kernel` is passed to `pip install -e`; the Go `lingtai/` repo is a workspace marker, not a Python package.
- **`tui/internal/config/venv.go:437-449`** — `CheckUpgrade`: thin wrapper over `UpgradePythonRuntime(globalDir, false, ...)` that returns `true` only when a real GitHub-release upgrade or dev-mode conversion was verified post-install. This is a **mutating** operation gated on explicit human consent for the current launch — it must only be invoked via `main.go`'s shared startup-update preflight (`maybeCheckAndPromptKernelUpgrade`, which prompts only after the read-only `InspectKernel` below reports an actionable update; runs for EVERY default interactive launch — existing project, first-run, and the no-project launcher alike, not only "returning users") or an explicitly-invoked path such as `doctor`/`self-update`/`/update`, never automatically. Any failure is silent so the TUI can still launch.
- **`tui/internal/config/kernel_update.go:39-138`** — `InspectKernel(globalDir) KernelStatus` (thin wrapper, `39-41`) over `inspectKernel` (`43-138`): **read-only** kernel version check — no pip/uv/brew command, ever. Reuses the same probes and strict `CompareReleaseVersions` classification as the mutating path so the two cannot drift. `NeedsUpdate` is true only for a missing/broken venv (repair is itself the "update") or when a strict installed release is older than the latest kernel GitHub release. Editable/dev checkouts, equal versions, installed versions newer than the latest published release, and non-release versions do not prompt or downgrade. `main.go`'s `runVersionPreflight` calls this — via `maybeCheckAndPromptKernelUpgrade` — for EVERY default interactive launch, before the no-project decision gate, whether or not a project currently exists, interactive or not, before ever deciding whether to prompt. install.sh installs the kernel by default, so first-run is not exempted.
- **`tui/internal/config/kernel_update.go:151-210`** — `RunKernelUpdate(globalDir, force) DoctorReport` (thin wrapper, `151-153`) over `runKernelUpdate` (`155-210`): the mutating kernel-only apply step — venv repair (mirroring `checkPythonRuntime`) plus `UpgradePythonRuntime`, but never the TUI binary (no brew) or file-search sidecar. Shared by `main.go`'s consent-driven startup upgrade, the `/update` interactive command (`tui/internal/tui/update.go`), and available to a future `/doctor` gated heal. `RunDoctorUpdate` (below) is left independent and unchanged for existing `doctor`/`self-update` callers.
- **`tui/internal/config/venv.go:458-481`** — `RuntimeReadyError` / `RuntimeReady(globalDir) error`: the sole readiness-check surface for every caller that is NOT the interactive startup preflight. **Read-only** — delegates to `NeedsVenv` and never creates, repairs, or upgrades anything. Returns nil when the managed venv exists and `lingtai` is importable; otherwise returns an actionable `*RuntimeReadyError` so the caller can surface a clear message instead of silently installing/repairing. There is deliberately no automatic "ensure the runtime" function any more (`EnsureRuntime`/`EnsureRuntimeQuiet`/`ensureRuntimeWithOptions`/`RuntimeEnsureOptions` were removed): install.sh installs the kernel by default, and the ONLY place the TUI may automatically install or repair it is `main.go`'s shared interactive startup preflight (`runVersionPreflight` → `maybeCheckAndPromptKernelUpgrade` → consent-gated `RunKernelUpdate`). Every other caller — returning-user `prepareApp`, the first-run wizard, headless spawn, and the post-Create project-launch phase — calls `RuntimeReady` instead, so a declined or absent runtime is never silently repaired behind that decision.
- **`tui/internal/config/venv.go:646-1047`** — `RunDoctorUpdate` runtime path: verifies the TUI binary against the latest GitHub release, reports the detected install method, routes forced TUI updates through `RunTUIUpdate`, repairs a missing/broken/confirmed-mismatched runtime venv, then runs `UpgradePythonRuntime(force=true)`, and asks the kernel-owned marker command to write/refresh after successful probes or upgrades. Marker check errors are surfaced as warnings but do not delete the managed venv. All command stdout/stderr is captured after command completion and surfaced; nothing is silently swallowed.
- **`tui/internal/config/venv.go:771-910`** — `detectTUIInstallMethod` and helpers: read `~/.lingtai-tui/install.json` source metadata (`lingtai.tui.install/v1`) and match it against the running executable (including the `lingtai` alias symlink in `bin_dir`), then fall back to Homebrew path/env detection (`HOMEBREW_PREFIX`, common Homebrew/Linuxbrew prefixes) or `unknown/other`. Source metadata wins over Homebrew-looking paths so source installs into a Homebrew bin dir are still reported as source — including a bin dir that a prior Homebrew-to-native migration (see `tui_updater.go` below) just installed into, since that migration writes exactly this `install.json` shape. **When valid source metadata exists but does NOT match the running executable, and that executable still resolves as Homebrew** (the common Apple-Silicon case: `/opt/homebrew/bin` precedes install.sh's default native bin dir on PATH), `TUIInstallInfo.DuplicateNativeInstall`/`DuplicateNativeDetail`/`DuplicateNativeTarget` are set instead of silently discarding the mismatch — `DuplicateNativeTarget` is the verified native binary path kept as a structured field (not parsed back out of `DuplicateNativeDetail`'s prose) so `tui_updater.go`'s cleanup primitive can re-resolve PATH against it after a Homebrew uninstall. `Method` stays `TUIInstallMethodHomebrew` (the resolved binary really is still Homebrew's), but every caller (startup, doctor, self-update) checks this field first and surfaces the truthful "native installed, migration not complete, remove Homebrew yourself" state instead of re-offering or re-running the migration.
- **`tui/internal/config/tui_updater.go`** — `TUIUpdater` interface plus `RunTUIUpdate` / `RunManualTUIUpdate` backend routing. The Homebrew backend (`homebrewTUIUpdater.Upgrade`) no longer runs `brew upgrade`; it migrates the install to LingTai's native installer instead. If `opts.Install.DuplicateNativeInstall` is already set (a prior migration attempt already installed and verified a native binary that Homebrew still shadows on PATH), `Upgrade` short-circuits immediately — it does **not** re-run install.sh — and goes straight to the shared `attemptHomebrewCleanup` primitive described below. Otherwise it runs `nativeMigrationInstallCommand`'s version-pinned raw release `install.sh --update --prefix <native-prefix> --version <tag> --non-interactive` contract, which accepts and updates existing managed runtime/receipt state in place while preserving the exact tag and keeping the native prefix outside Homebrew, then verifies the new `install.json` source metadata, the binary version at the new `bin_dir`, and the Python runtime — the same verification shape as the source backend below. **Before declaring `Updated=true` it resolves `lingtai-tui` on PATH (`opts.LookPath`, defaults to `exec.LookPath`) and compares it against the newly installed binary.** When PATH still resolves elsewhere (or `LookPath` errors), it sets `NeedsManualCleanup=true` and reports the honest "native installed, Homebrew still resolved first on PATH" state instead, without ever attempting cleanup — this is the fix for the Apple-Silicon case where install.sh's default bin dir (`~/.local/bin` or `/usr/local/bin`) is not earlier on PATH than `/opt/homebrew/bin`, so a "successful" migration would otherwise be a no-op the shell never runs.
  **Homebrew cleanup decision (`attemptHomebrewCleanup`, `tui_updater.go`)** is the single owning primitive for removing the old Homebrew install, reached from both the pre-existing-duplicate short-circuit above and immediately after a fresh migration's PATH takeover is confirmed — one primitive, not drifted copies, per the Homebrew formula-uninstall contract (Jason Telegram 9786/9792). It never runs brew itself: `TUIUpdateOptions.ConfirmHomebrewCleanup` (a `func() bool`) is nil for every non-interactive caller (`RunDoctorUpdate`'s forced `checkTUI` call, `RunManualTUIUpdate`), so those paths only ever report the truthful pending-cleanup guidance and the exact manual `brew uninstall lingtai-ai/lingtai/lingtai-tui` command — never prompting, never uninstalling. Only the interactive startup path (`tui/upgrade.go`'s `handleHomebrewTUIUpgrade`, via `homebrewCleanupPrompt`) supplies a real callback, and only an explicit "y" answer to the concrete `Remove the old Homebrew installation now? [y/N]` prompt reaches `TUIUpdateOptions.UninstallHomebrew` (defaults to `execHomebrewUninstall`: `exec.Command("brew", "uninstall", "lingtai-ai/lingtai/lingtai-tui")`, explicit executable+argv, never a shell string — the only brew invocation anywhere in this package). A failed uninstall, or a post-uninstall `opts.LookPath("lingtai-tui")` that still does not resolve to the verified native target, both keep `NeedsManualCleanup=true`; only a fresh PATH lookup matching the native binary — never the still-running Homebrew process — clears it. `Updated=true` (the TUI binary itself migrated) and `NeedsManualCleanup=true` (Homebrew removal still pending, either declined or failed) can both be true at once; callers must keep re-surfacing the pending state rather than treating `Updated` alone as full completion. Only once PATH takeover is confirmed does `detectTUIInstallMethod` report the install as source/user-local on the next call, so subsequent updates route through the source backend instead of this one — until then, every update entry point keeps re-detecting the duplicate/shadowed state via `DuplicateNativeInstall` above, including re-asking the cleanup question on every interactive launch. The source backend (`sourceTUIUpdater.Upgrade`) requires a known release tag, reads source metadata from `install.json`, runs the versioned `install.sh --update --prefix <prefix> --version <tag> --non-interactive` contract, then verifies the new binary version, refreshed metadata, and runtime venv health. Unknown installs remain explicit unsupported command results instead of running brew. Callers keep version checks/prompting; the backend owns only the mutation-or-guidance for one install method.
- **`tui/internal/config/venv.go:1301-1504`** — `UpgradePythonRuntime`: checks the installed Python `lingtai` runtime. If a local dev checkout is discovered and the runtime is not already editable for that checkout, it runs an editable install before release comparison. The additive provenance gates recognize release bundles and cross-platform current-main installs and skip replacement. Only metadata with no recognized provenance reaches the ordinary release path. That path obtains the latest version from GitHub Releases and uses `CompareReleaseVersions`; equal releases may be reinstalled only for an explicit forced repair, while newer installed releases and non-release versions are never replaced or downgraded. An actionable update installs the latest release's checksum-pinned GitHub wheel (`--upgrade`), never a package name from an index, then verifies the imported version and refreshes the runtime marker best-effort.
- **`tui/internal/config/venv.go:517-629`** — `DoctorOptions` / `CommandRunner` / `TUIInstallMethod` / `TUIInstallInfo` / `tuiInstallMetadata`: dependency-injection seams so tests stub brew/pip/python/home/env without dialing the network, plus the small install-method result type used by doctor reporting and updater routing. `tuiInstallMetadata` carries `repo_url`, `requested_ref`, `resolved_ref`, `resolved_commit`, `stamped_version` so the source updater can drive and re-verify `install.sh --update`. Production callers leave the seams nil and get real `exec.Command` + `http.Client` + `os.UserHomeDir` / `os.LookupEnv`.
- **`tui/internal/config/venv.go:1018-1119`** — `checkFileSearchNative` / `FileSearchStatus` / `timeoutCommandRunner` / `FileSearchNativeStatus`: asks the managed Python runtime which file-search backend it will use (`RustFileIOBackend` sidecar vs Python fallback) and reports both packaged sidecar status and local Cargo availability for `/doctor` / startup guidance. The probe runs through a `timeoutCommandRunner` (3s default) so startup and `/doctor` cannot hang on a slow or broken managed Python runtime. A `ModuleNotFoundError` for `lingtai.services.file_io_sidecar` (a runtime that predates the Rust sidecar release) is reported as `FileSearchStatus{Unsupported: true}` rather than an error; `checkFileSearchNative` then emits a single `DoctorInfo` line and the report stays healthy.
- **`tui/internal/config/venv.go:384-425`** — `EnsureAddons`: reads `init.json`'s `addons` map and verifies each addon is importable as `lingtai.addons.<name>`. Errors identify the missing addon and direct users to repair the managed runtime with the official LingTai installer rather than a package-name pip command.
- **`tui/internal/config/venv.go:340-363`** — `CheckTUIUpgrade`: compares running TUI binary version against latest GitHub release. Returns tag if upgrade available. Used by the startup-time prompt in `main.go`.
- **`tui/internal/config/venv.go:1177-1216`** — `CompareReleaseVersions` / `ReleaseComparison`: classifies strict `vX.Y.Z` release comparisons as update-available, up-to-date, current missing, dev build, current non-semver, or latest non-semver; `/doctor` uses this so hash-like current versions do not look up-to-date.
- **`tui/internal/config/venv.go:268-290`** — `linkLingtaiCLI`: symlinks `lingtai` CLI from venv into brew prefix or `~/.local/bin`.

Added for the no-project launcher's zero-write startup gate (`tui/internal/tui/launcher.go`), which must know where the global dir *would* live without creating it merely by asking.

  3. `preset.Bootstrap(globalDir)` — copy preset resources
  4. `tui.ExportCommandsJSON(globalDir)` — export slash commands
  5. `maybePromptRustToolchain(globalDir)` — one-time optional Rust/Cargo prompt when native file search is unavailable and Cargo is missing

## Notes

- **MCP packages are dependencies of `lingtai`.** The `lingtai` distribution bundles `lingtai-kernel` + all addon MCPs, so installing the kernel release wheel upgrades everything. Users never install MCP packages individually. The wheel comes from the kernel GitHub release manifest, not PyPI.
- **No automatic install/repair path exists outside the preflight.** `config.RuntimeReady` runs on every TUI launch (returning-user `prepareApp`), first-run bootstrap, headless spawn, and the post-Create project-launch phase — but it is READ-ONLY: it never creates, repairs, or upgrades anything, it only reports whether the runtime is usable. The kernel version check AND its consent-gated install/repair/update all happen exactly once, earlier, in `main.go`'s shared `runVersionPreflight` — for EVERY default interactive launch (existing project, first-run, or the empty-directory no-project launcher), not only "returning users," and before any of `prepareApp`'s work. Only an explicit "y" to that preflight's `[y/N]` prompt (real stdin TTY only, per-launch, never persisted) calls the mutating `config.RunKernelUpdate`. If the human declines, or the launch is non-interactive (first-run reached via headless tooling, `spawn`, etc.), the runtime may still be absent/broken when `prepareApp`/the first-run wizard/headless spawn/post-Create launch later check `config.RuntimeReady` — that decline is never silently overridden by a second, hidden install; each of those callers surfaces the actionable `*RuntimeReadyError` instead. The same mutating logic — minus any prompt, since explicit invocation IS the consent — is reachable via `lingtai-tui doctor` / `/doctor` (`RunDoctorUpdate` with `ForceTUI=true` / `ForcePython=true`, surfacing every command's stdout/stderr) and the dedicated `/update` command (`tui/internal/tui/update.go`), which uses `InspectKernel`/`RunKernelUpdate` directly for a kernel-only confirm-then-update flow.
- **Dev mode conversion:** local dev workspaces are enabled explicitly with `$LINGTAI_DEV_ROOT` (for example, `LINGTAI_DEV_ROOT=~/work/GitHub` when that directory contains sibling `lingtai-kernel/` and `lingtai/`). If configured and valid, the runtime should track `lingtai-kernel` editable. Existing editable installs and detected dev checkouts report `NeedsUpdate=false` to avoid a misleading release-update prompt or reinstall on every launch. No common-directory auto-scan runs by default, so ordinary users with source clones are not silently switched into editable mode.
- **`uv` preferred over `pip`:** all pip operations prefer `uv` if available (faster, can auto-download Python).
- **`.env` is no longer clobber-rewritten.** Both `WriteEnvFile` (managed API keys) and `SetEnvVar` (single unmanaged key, e.g. the soul-flow opt-in) preserve everything they don't own: comments, blanks, unrelated vars, and file permissions. This is what lets `LINGTAI_SOUL_FLOW_ENABLED` — written by the first-run/`/setup` wizard opt-in via `preset.GenerateInitJSONWithOpts` — survive a later API-key save. The kernel reads this var from process env (populated from `env_file` at agent boot); the delay/cadence in `manifest.soul.delay` is cadence-only after opt-in, not an on/off switch.
- **`related_files` is this package's full inventory.** The repo-wide no-orphan rule (root `ANATOMY.md`, `## Anatomy convention`) requires every tracked file here to appear in the frontmatter above, and `TestArchitectureDocumentsCoverEveryTrackedFile` (`tui/architecture_documents_test.go`) fails when one is missing. The body stays the curated architectural map: adding a file does not oblige a new row above, but adding its `related_files` entry in the same commit is mandatory — and deleting a file means deleting its entry.
